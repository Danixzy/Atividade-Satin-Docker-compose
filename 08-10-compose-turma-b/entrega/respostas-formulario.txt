2) FALHAS ENCONTRADAS
=====================================================================
FALHA 1: o portal encaminha /api/ para 127.0.0.1, ou seja, para ele mesmo
- Sintoma: 502 Bad Gateway em /api/saude, /api/livros e /api/reservas.
- Evidência: log do portal "connect() failed (111: Connection refused) ... upstream: http://127.0.0.1:3000/saude"; o default.conf gerado no container contém "set $destino http://127.0.0.1:3000;".
- Causa: API_URL: "http://127.0.0.1:3000". Dentro do container do portal, 127.0.0.1 é o próprio Nginx. A API está em outro container e deve ser acessada pelo nome do serviço na rede do Compose (o template já usa o DNS interno, resolver 127.0.0.11).
- Alteração: API_URL: "http://api:3000".
- Resultado: o 502 continuou, mas o log passou a mostrar upstream "http://172.18.0.2:3000/saude", o IP do container api. O nome passou a resolver e apareceu a falha 2.

FALHA 2: a API escuta na porta 3001 e o portal procura na 3000
- Sintoma: depois da correção 1, ainda "Connection refused" em 172.18.0.2:3000.
- Evidência:
    $ docker compose logs api                          -> {"evento":"inicio","porta":3001}
    $ docker compose exec api netstat -ltn             -> :::3001 LISTEN
    $ docker compose exec portal wget -qO- http://api:3000/saude -> Connection refused
    $ docker compose exec portal wget -qO- http://api:3001/saude -> {"status":"ok","turma":"B"}
    docker compose ps mostra "3000/tcp" (EXPOSE 3000 do Dockerfile), que não é a porta usada de fato.
- Causa: a variável PORT: "3001" no compose sobrescreve o padrão 3000 do server.ts.
- Alteração: PORT: "3000", alinhado com o EXPOSE 3000 do Dockerfile e com o API_URL.
- Resultado: /api/saude respondeu 200 {"status":"ok","turma":"B"} e /api/livros devolveu os 3 livros.

FALHA 3: as reservas se perdem no docker compose down
- Sintoma: com as falhas 1 e 2 corrigidas, a reserva era registrada, mas sumia depois de down/up.
- Evidência:
    POST /api/reservas {"livroId":2,"nome":"RA-TESTE"} -> 201; o arquivo /app/registros/reservas.json passou a conter a reserva
    $ docker compose down && docker compose up -d
    $ curl http://localhost:8081/api/reservas -> []
    $ docker compose exec api ls -la /app/registros -> diretório vazio
    $ docker inspect turma-b-api-1 --format "{{json .Mounts}}" -> só o bind ./dados:/app/dados (ro), nenhum volume em /app/registros
- Causa: a API grava as reservas em /app/registros/reservas.json, na camada gravável do container, que é removida pelo down.
- Alteração: volume nomeado "registros:/app/registros" no serviço api, declarado em volumes: no nível raiz.
- Resultado: a reserva continuou registrada após down/up, e o volume turma-b_registros sobreviveu ao down.

HIPÓTESES TESTADAS E DESCARTADAS
- A API estaria caindo, já que o Node roda server.ts direto, sem compilar: descartada. docker compose ps mostra a API "Up", o log mostra {"evento":"inicio"} e wget http://api:3001/saude de dentro do portal respondeu ok.
- O Nginx não resolveria o nome "api" (DNS): descartada. Depois da correção 1, o log mostrou upstream 172.18.0.2, ou seja, o nome resolveu.
- O rewrite de /api/ no Nginx estaria errado: descartada. O upstream no log já aparece sem o prefixo (/saude, /livros, /reservas), e depois das correções as rotas responderam 200. O template do portal não precisou ser alterado.
- O ":ro" no volume ./dados impediria gravar as reservas: descartada. A API grava em /app/registros, não em /app/dados, e o POST respondeu 201. O ":ro" foi mantido porque a API só lê o catálogo.
- Publicar a porta da API para testar: não usei, por causa do critério 4. Testei a API de dentro do portal com docker compose exec portal wget.

    build: ./api
    environment:
      PORT: "3000"
    volumes:
      - ./dados:/app/dados:ro
      - registros:/app/registros
  portal:
    build: ./portal
    ports:
      - "127.0.0.1:8081:80"
    environment:
      API_URL: "http://api:3000"
    depends_on:
      - api
